# 根因追蹤

處理「症狀在 A，但原因藏在很遠的 B」的問題——避免直接在症狀處打補丁，而是沿著因果鏈往回追，找到真正該修的地方。

## 何時使用此技能

- 同一個 bug 修好又復發，或修完之後在別的地方冒出新問題
- 錯誤訊息／症狀本身看起來很表面（例如「畫面空白」「數字對不上」），但不知道源頭在哪
- 懷疑自己正在對症狀打補丁，而不是修根本原因
- 系統性問題：不是單一次意外，而是某個模式反覆出現

## 追蹤方法

1. **鎖定症狀，不急著猜原因**：先精確描述「觀察到什麼」（什麼時候發生、多頻繁、
   有沒有規律），避免一開始就跳到某個假設上
2. **建立因果鏈**：從症狀往回問「這是什麼造成的？」，每往回一步就寫下來，
   直到問到「為什麼」問不下去為止（類似「五個為什麼」，但不限定次數，
   問到證據能支撐停下來為止）
3. **每一步都要有證據，不是憑猜測**：
   - 能重現的問題，先重現它，觀察實際行為而非猜測行為
   - 查日誌／log／版本歷史，找出問題第一次出現的時間點
   - 用「排除法」縮小範圍：能不能關掉/隔離某個變因後問題消失？
4. **區分「觸發原因」與「根本原因」**：
   - 觸發原因：這次是什麼條件引發的（例如某個特定輸入）
   - 根本原因：為什麼系統在這種條件下會出問題（設計缺陷、假設錯誤、邊界條件沒處理）
   - 只修觸發原因等於沒修，還會用別的觸發條件再爆一次
5. **驗證假設**：找到疑似根因後，先驗證「如果真的是這個原因，修了之後症狀應該消失」，
   實際驗證過再動手修，避免「感覺對了」就直接下結論

## 輸出格式

```
🔍 根因追蹤：<問題描述>
症狀：<觀察到的表面現象>
因果鏈：症狀 ← 直接原因 ← ... ← 根本原因
證據：<支持這條因果鏈的具體證據，不是推測>
根本原因：<最終判定>
建議修法：<修根因的做法> vs <只修症狀會有什麼問題>
```

## 注意事項

- 這是分析方法，不是自動化工具——每一步的假設都要講出來讓使用者確認，
  不要默默跳過驗證直接下結論（對應 FABLE-PROTOCOL 的 Orient 亮假設原則）
- 遇到「重大結論」（例如判定某個根因會影響生產環境）時，先過對抗性審查
  （adversarial-review 技能）再採信，不要只憑一次推理就下定論
