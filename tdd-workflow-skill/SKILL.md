# 測試驅動開發（TDD）工作流

以「紅燈 → 綠燈 → 重構」的循環開發功能，確保每一段程式碼都有測試證明它真的有效，而不是寫完程式碼才回頭補測試。

## 何時使用此技能

- 使用者明確要求用 TDD 方式開發
- 修 bug 時想要「先證明 bug 存在，再證明修好了」（fail-then-pass 證據）
- 新增功能邏輯，且該邏輯有明確、可驗證的輸入輸出
- 專案已有測試框架、且測試是可信賴的驗收標準

## 核心循環：Red → Green → Refactor

1. **Red（先寫一個會失敗的測試）**
   - 針對「還沒實作的行為」寫一個測試案例
   - 執行測試，確認它「因為功能還沒做」而失敗——不是因為測試本身寫錯
   - 這一步的重點是先把「什麼叫做對」講清楚，再去做

2. **Green（寫最少量的程式碼讓測試通過）**
   - 只寫剛好能讓這個測試通過的程式碼，不要順便做其他還沒被測試覆蓋的事
   - 執行測試，確認變成通過（綠燈）
   - 這一步不追求優雅，先求「對」

3. **Refactor（在測試保護下重構）**
   - 測試通過後，回頭整理程式碼——去重複、改名、抽函式
   - 每次重構後重新跑測試，確保行為沒有被改變
   - 測試是這一步的安全網：只要測試持續通過，就能放心調整內部結構

4. **重複**：進到下一個還沒被覆蓋的行為，回到步驟 1

## 修 bug 時的用法（fail-then-pass 證據）

修 bug 是 TDD 最直接的應用場景：

1. 先寫一個能重現 bug 的測試，執行它，**展示它確實失敗**（證明 bug 真實存在，不是猜的）
2. 修正程式碼
3. 重新執行同一個測試，**展示它現在通過**
4. 這樣就有完整的「修復前失敗、修復後通過」證據，而不是只憑感覺說「應該修好了」

## 輸出格式

每完成一輪循環，簡短回報：

```
🔴 Red：<測試名稱> — 失敗原因：<功能尚未實作/bug 確實存在>
🟢 Green：<做了什麼最小實作> — 測試通過
🔧 Refactor：<有沒有重構，改了什麼>（若這輪沒有需要重構的部分可省略）
```

## 注意事項

- 沒有測試框架的專案，先確認測試怎麼跑（`npm test`、`pytest` 等），不要假設
- 不要為了「有測試」而寫瑣碎、不驗證任何真實行為的測試
- 這個技能只涵蓋開發流程本身；若需要診斷「為什麼測試一直失敗」，
  搭配本倉庫的 test-fixing-skill 使用
