# 測試修復

面對失敗的測試案例時，先判斷失敗原因的類型，再選擇對應的修法——目標是讓測試真正反映正確行為，而不是用任何手段讓它變綠燈。

## 何時使用此技能

- CI 顯示測試失敗，需要診斷並修復
- 改了程式碼之後，原本通過的測試突然失敗
- 測試長期不穩定（flaky），有時過有時不過
- 想確認「這個測試失敗到底是誰的問題」

## 診斷流程

1. **讀懂失敗訊息，不要跳過**：先完整看錯誤訊息、堆疊追蹤、實際值 vs 預期值的差異，
   而不是憑檔名或測試名稱猜測原因

2. **分類失敗原因**（這一步決定怎麼修，不能跳過）：
   - **程式碼有 bug**：實作邏輯錯誤，測試正確地抓到了問題 → 修程式碼
   - **測試過時**：需求或行為已經合理地改變，測試還停留在舊行為 → 更新測試的預期值，
     但要能說明「為什麼舊預期值不再適用」
   - **測試本身寫錯**：測試邏輯有誤（例如比對錯欄位、非同步時序問題、假設了不保證的執行順序）
     → 修測試
   - **環境／依賴問題**：外部服務、版本、設定造成的不穩定，不是程式邏輯問題 → 修環境或加隔離
   - **Flaky（不穩定）**：與時間、隨機性、並行有關，同樣輸入有時過有時不過 → 找出不確定性來源
     （未等待非同步完成、共用可變狀態、依賴系統時間）並消除它

3. **修復並驗證**：
   - 修完後至少連續執行測試數次確認穩定通過（尤其 flaky 測試不能只跑一次就宣告修好）
   - 若是修程式碼，確認其他相關測試沒有被連帶弄壞

## 絕對禁止的「修法」

- ❌ 刪除或跳過（skip）失敗的測試來讓 CI 變綠，除非能明確說明這個測試本身已經失效或重複
- ❌ 放寬斷言（assertion）到「幾乎什麼都會過」的程度，讓測試名存實亡
- ❌ 加 `sleep`／重試迴圈掩蓋 flaky 根因，而不去找不穩定性的真正來源
- 上述任何一種「讓測試消失而非讓它正確」的做法，等於製造一個看起來測試齊全、
  實際上什麼都沒驗證的假象

## 輸出格式

```
🧪 測試修復：<測試名稱>
失敗原因分類：<程式碼bug／測試過時／測試寫錯／環境問題／flaky>
根本原因：<具體是什麼>
修法：<改了什麼，為什麼這樣改是對的而不是繞過問題>
驗證：<重跑結果，flaky 類需附多次執行紀錄>
```

## 注意事項

- 診斷「為什麼會這樣」時，若原因不明顯，可搭配本倉庫的 root-cause-tracing-skill
  做更深入的因果鏈追蹤
- 開發新功能時建議直接用 tdd-workflow-skill 避免產生一堆事後才修的測試
